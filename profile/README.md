<p>动态住宅 IP 不是万能钥匙，它解决的是地址需要变化的问题，而不是地址需要稳定的问题。用错地方，钱花了、稳定性还下降了。这篇按团队形态分三类——短时批处理、多地区比价、集成转售——每类给一套轮换参数和常见坑，最后把轮换策略拆成四个可调参数，方便你按自己的请求模型去配。</p>

<h2>一、先看团队形态：三类需求对应三种轮换逻辑</h2>
<p>选动态还是静态，答案不在产品页上，在你的请求模型里。判断只需要回答三个问题：单个任务的持续时间有多长、请求是否需要在多个地区同时发出、失败重试的代价有多高。三个答案组合起来，基本就锁定了轮换粒度。</p>
<h3>任务时长决定会话粘性</h3>
<p>一个任务如果三十秒内能跑完，地址换不换无所谓；如果一次任务要跑十分钟、中间还要保持上下文，就必须用粘性会话，让同一个任务固定在同一出口上。很多动态不稳的抱怨，本质是把长任务放在了每请求轮换的模式上。</p>
<h3>地区分布决定池的宽度</h3>
<p>只在一个国家跑，池子窄一点没关系；要在五六个国家同时采数据，池的国家覆盖和每国可用量就变成硬指标。问供应商时要具体到某国晚八点的可用地址数，而不是全球多少万 IP。</p>
<h3>重试代价决定冗余度</h3>
<p>失败重跑一次成本很低的场景，可以容忍较高的轮换失败率；一旦失败就要人工介入的场景，必须留出备用池。这条决定了你要不要为冗余付钱，也决定了预算的上下限。</p>

<h2>二、短时批处理团队：会话级轮换怎么设</h2>
<p>这类团队的典型画像是有几万条待处理地址，跑完就结束，明天换一批。诉求是吞吐和单位成本，对地址稳定性要求最低，但对手动干预的容忍度也最低——没人愿意半夜起来重启脚本。</p>
<h3>把轮换绑在任务上，而不是绑在请求上</h3>
<p>每个任务开始时申请一条地址，任务结束释放。这样既不会在任务中途换出口导致上下文断裂，也不会让一条地址被长期占用。实现上用带 session 参数的网关地址即可，注意在代码里显式释放，否则池子会被占满，后面的任务只能排队。</p>
<h3>失败要分类，不要一律重试</h3>
<p>把失败分成三类：拿到 5xx 的重试即可，超时的换地址重试，返回 4xx 的先别看网络。三类混在一起无脑重试，会把池子里的地址快速消耗掉，还会拉高整体失败率，最后连统计都失真。</p>
<h3>按结果淘汰地址</h3>
<p>记录每条地址的失败次数，超过阈值就标记为不可用并上报。动态池的特点是质量不均，靠人工抽查发现不了问题，只能靠统计。淘汰规则写成代码，每天跑一次，比人工盯有效得多。</p>

<h2>三、多地区比价团队：地理分布与时区节拍</h2>
<p>比价类业务的核心是从目标地区看过去，所以地区准确性比地址数量更重要。用错国家的出口，拿到的价格、库存、页面语言都可能是错的，数据直接作废。</p>
<h3>先验证地区，再谈速度</h3>
<p>拿到地址后先用公开的 IP 归属库核对国家与城市，再看目标站点返回的货币和语言是否符合预期。这一步花两分钟，能省掉后面几小时的数据清洗，也能避免把错误结论带进决策。</p>
<h3>跟着目标时区排班</h3>
<p>目标市场的上午十点和你的凌晨三点是同一时刻。任务调度要按目标时区安排，既符合业务语义，也避开本地出口的拥塞高峰。跨时区团队尤其容易在这里出错，建议在调度器里显式写上时区。</p>

<h2>四、集成转售团队：池容量与并发配比</h2>
<p>把住宅出口集成进自己的产品再卖出去，考的是隔离和计量。一个客户把并发打满，不能影响其他客户；计费口径要能对上每一次调用，否则月底对账会变成灾难。</p>
<h3>按客户划分独立子池</h3>
<p>每个客户分配独立的地址段或独立的上游账号，配额单独计算。共享一个大池看似省钱，一旦某个客户跑异常流量，整池地址的信誉都会被拖累，恢复起来比换一家供应商还慢。</p>
<h3>并发配比留三成余量</h3>
<p>上游给你的并发上限，不要按满额卖给客户。留出三成余量应对突发和重试，否则高峰期会出现互相抢占，表现为所有人一起变慢。计量要落到请求级，记录客户标识、地址、耗时、结果码，既是计费依据也是定位证据。</p>

<h2>五、轮换策略的四个可调参数</h2>
<p>不管哪类团队，调优最终都落在四个参数上。把它们理解清楚，比反复换供应商更有效。</p>
<h3>轮换间隔与粘性时长</h3>
<p>从每请求换到每小时换，跨度很大。经验值：短任务用任务级，长会话用十到三十分钟，登录态相关的场景尽量不换。粘性时长指一条地址被同一会话连续占用的最长时间，通常取业务单次会话时长的 1.5 倍，设得太短上下文会断，设得太长地址被污染后影响面扩大。</p>
<h3>失败切换阈值与池内淘汰规则</h3>
<p>连续失败几次后强制换地址，设 2 到 3 次比较稳妥；设 1 次会因为偶发超时频繁切换，反而更不稳。淘汰规则按日统计每条地址的成功率，低于八成的暂时移出池子，观察一天再决定是否恢复。</p>

<h2>常见问答</h2>
<h3>动态住宅 IP 一定比静态便宜吗？</h3>
<p>答：多数按流量计费的动态池单价看起来低，但实际成本取决于你的请求体积和重试率。图片、文件类请求多的业务，流量费会很快超过静态独享的月费。要按自己的月度流量算一遍再比较。</p>
<h3>轮换越频繁越安全吗？</h3>
<p>答：不是。频繁轮换会让同一账号的登录地和出口不断变化，对需要保持会话一致性的场景反而是负担。轮换频率应当由任务时长和会话需求决定，而不是由看起来更隐蔽决定。</p>
<h3>一个动态池能同时给多个项目用吗？</h3>
<p>答：技术上可以，管理上不建议。不同项目的请求特征混在一个池里，出问题时无法区分是谁造成的，配额也容易被一个项目吃光。至少按项目分池，成本增加有限。</p>
<h3>怎么判断池子里的地址质量？</h3>
<p>答：抽样加统计。每天抽几十条地址查 ASN 与类型标签，同时统计全池的成功率分布。平均值没意义，要看尾部——最差的那 10% 决定了你的重试成本。</p>
